# 同步一致性（1.2.0）

FleetDispatch App 以事件（`POST /events`）寫入、以全量（`GET /snapshot`）與增量（`GET /changes`）讀取。這份文件說明 1.2.0 起主機如何保證「每個事件只套用一次、授權與寫入看到同一個版本、不會因並行而遺失修改」。協定細節見 [`protocol.md`](protocol.md) §4、§6、§7.1。

## 1. 冪等（事件只套用一次）

- 鍵：權杖對應的裝置 ID ＋ 事件 `id`（1–100 字元）。
- 第一次處理時記下結果（`fd_processed_events`）：寫入成功的結果與資料、歷史在**同一個交易**提交；拒絕、略過、衝突的結果另外記下。
- 重送同一個事件：直接回傳第一次的結果並加上 `"duplicate": true`，不重複寫入、不重複稽核與歷史、不重複連鎖刪除。
- 保留 30 天（App 的重送通常在幾分鐘內）。

用途：App 送出後沒收到回應（網路中斷、逾時）時重送整批，不會重複套用。

## 2. 授權與寫入看到同一個版本

| 實作 | 方式 |
| --- | --- |
| PHP | 每筆事件一個交易，先取得全主機寫入鎖（SQLite `BEGIN IMMEDIATE`、MySQL 鎖定序號列）再讀取、授權、寫入 |
| Docker／Node、Cloudflare D1 | 樂觀並行控制：讀取 → 授權 → 以「讀取時的序號」作為寫入條件（同一個 batch／交易）。期間被別的請求改過時寫入不生效，重讀、重新授權後重試；連續 3 次失敗回 `503 busy`（整批可安全重送，見 §1） |

例：駕駛修改自己的車趟時，管理員同時把車趟改派給別的駕駛——舊版本可能以「改派前」的狀態通過授權並覆寫；1.2.0 起寫入會因序號不同而失敗，重讀後依改派後的狀態判斷。

## 3. 版本（revision）與衝突

- 每筆資料有 `revision`：新資料是 1，每次寫入（含刪除、連鎖刪除、網頁管理的修改）加 1。`GET /changes` 的每筆變更與 `GET /snapshot` 的 `revisions` 帶目前的版本。
- 事件可帶選填的 `expectedRevision`：與主機上的版本不同時不寫入，回傳 `conflict`（`revision-mismatch`）與目前的版本摘要；用戶端可以重新載入、比較後再送出或請使用者決定。
- 不帶 `expectedRevision`（App 8.0 與 6.0／7.0 的區網裝置）時照舊以「最後寫入者勝」：事件時間嚴格大於主機上的修改時間才寫入。

## 4. 伺服器端的業務規則

- 還有未回車車趟的車輛不能刪除（`vehicle-has-active-trips`）。App 本身也不允許；主機再檢查一次，避免舊版或離線很久的裝置送來的刪除造成資料不一致。
- 刪除車輛時連鎖刪除同車牌的車趟、保養、保養項目、工單、巡檢（車趟的資料格式只有車牌，沒有車輛的 UUID，所以以車牌對應）。
- 最後一位有效的管理員不能被降級或解除配對：TypeScript 版把「其他管理員還在」寫成同一句 UPDATE 的條件，PHP 在寫入鎖內檢查——兩位管理員同時互相降級時至少留下一位。

## 5. 測試

`conformance/api.test.mjs` 的 1.2.0 項目在三種實作執行（Docker／Node、PHP＋SQLite、Cloudflare Workers 本機 D1）：冪等（重送不重複寫入、稽核、歷史；拒絕的結果也一致）、revision 與 conflict、修改前後歷史、兩位管理員同時互相降級、刪除有進行中車趟的車輛被拒絕。
