# 網頁管理：資料的查看與修改（1.2.0）

1.2.0 起，網頁管理除了裝置與配對碼，也可以查看、搜尋與修改主機上的資料。所有修改都經過主機的受控 API（[`protocol.md`](protocol.md) §7.2–7.7）：
瀏覽器不直接接觸資料庫，主機檢查權限、欄位、資料關聯與版本後，才在一個交易中寫入資料、修改前後歷史與稽核紀錄；App 以原本的同步取得修改。

## 1. 身分與角色（不是同一件事）

主機以「配對的裝置」為核心，**沒有使用者帳號系統**。下面幾個概念分開保存，網頁管理也分開顯示：

| 概念 | 存在哪裡 | 說明 |
| --- | --- | --- |
| 配對裝置 | `fd_devices`（每台 App 或瀏覽器一列） | 裝置 ID（由裝置提供）、名稱、平台、角色、權杖（只存雜湊）、最後連線時間、是否已解除配對 |
| 使用者帳號 | 不存在 | 主機不保存姓名、Email 或密碼。網頁管理的「登入」也是一台配對的瀏覽器（1.2.0 起權杖只放在 HttpOnly Cookie，[`protocol.md`](protocol.md) §13.1） |
| 駕駛人 | 資料（`fd_records` 的 `driver`） | App 建立的駕駛人資料（姓名、電話、證號…），與裝置無關；管理員可以把駕駛裝置**綁定**到一位駕駛人（`fd_devices.driver_uuid`） |
| 管理角色 | `fd_devices.role` | `admin`、`driver`、`viewer`，屬於裝置；同一個人的兩台裝置可以有不同角色 |
| 建立事件的身分 | `fd_devices.identity`（每次配對重新產生）、資料的 `created_by`、歷史的 `actor_identity` | 擁有權以這個身分判斷：裝置解除配對後以同一個裝置 ID 重新配對，不會繼承之前建立的資料 |

所以「某位使用者的車趟」在主機上是：**綁定這位駕駛人的車趟**（駕駛人詳情頁、`driverId` 篩選），或**某台裝置這次配對建立的資料**（`deviceId` 篩選）。

## 2. 可以修改什麼

欄位與限制寫在 [`spec/admin-entities.json`](../spec/admin-entities.json)（三種實作與網頁共用）。只有 `edit: true` 的欄位可以在網頁修改；其餘只顯示。
刻意不開放的項目：

| 項目 | 原因 | 怎麼做 |
| --- | --- | --- |
| 車輛的車牌 | 車趟、保養、工單、巡檢以車牌對應車輛；只改車輛會讓既有資料對不上 | 在 App 修改 |
| 駕駛人的姓名 | 沒有駕駛人 UUID 的車趟、巡檢與裝置綁定以姓名對應 | 在 App 修改 |
| 工單改為「已完成」 | App 完工時在同一個交易扣零件庫存、寫保養紀錄；只改狀態會漏掉這些 | 在 App 完工（網頁可以改成其他狀態，或重新開啟） |
| 工單、巡檢的明細；巡檢結果 | 結果由明細判斷；明細的編輯需要 App 的表單規則 | 在 App 修改 |
| 車趟改回出車中 | 回車後的里程、費用已被報表與保養計算使用 | 在 App 修改 |
| 用車申請的內容 | 申請只能核准或退回 | 網頁的「核准」「退回」 |
| 新增資料 | 1.2.0 不提供 | 在 App 新增 |

修改一律要填**原因**（寫進修改前後歷史），可以先**預覽差異**（`dryRun`），送出時帶「開始修改時的版本」（`expectedRevision`）——
期間被其他裝置改過時主機拒絕（`409 revision_mismatch`），網頁顯示目前的內容讓管理員重新比較。

## 3. 與 App 的同步

- 修改後的資料取得新的序號與版本，App 以 `GET /changes` 取得，與其他裝置的修改相同。
- 修改時間以主機的時間為準（至少比原本的修改時間晚 1 毫秒）。離線很久的 App 之後送來「比這次修改早」的修改時，依最後寫入者勝**略過**，
  不會蓋掉網頁的修改；修改前後歷史留下一筆 `ignored`（`stale`）的摘要，可以看到被略過的內容。
- App 8.1 送事件時帶 `expectedRevision`：版本不同時回 `conflict`，由 App 讓使用者決定（App 8.1 起）。App 8.0 不帶，照舊最後寫入者勝。
- 駕駛裝置只收到自己的車趟：網頁把車趟改派給另一位駕駛人後，原本的駕駛裝置收不到這筆修改，下一次全量同步（最多 6 小時）時移除。

## 4. 刪除

- 先看**影響預覽**：車輛會一併刪除同車牌的車趟、保養、保養項目、工單、巡檢；還有出車中的車趟時不能刪除。駕駛人的車趟保留駕駛姓名，不會被刪除。
- 刪除車輛時要帶預覽時的筆數（`expectedCascade`）：預覽之後又有新的資料時主機拒絕（`409 impact_changed`），請重新預覽——管理員看到的就是實際刪除的範圍。
- 車輛與連鎖刪除的資料在同一個交易改為墓碑：
  - Cloudflare D1、Docker／Node：一個 batch，連鎖刪除以集合式 SQL 完成（子資料再多也是固定幾句），前提（版本、沒有出車中的車趟、筆數）在同一個 batch 一開始檢查，
    不成立時整批都不寫（`fd_meta` 的 `guard` 旗標）。App 的刪除事件也改用同一個方式（1.1 是逐筆刪除，中途失敗會留下一半）。
  - PHP：全主機寫入鎖的交易。
- 網頁的刪除是永久刪除（墓碑，App 同步後刪除本機資料）。App 8.1 規劃的「封存／停用」不會刪除歷史車趟，見 App 的說明。

## 5. 用車申請的簽核

與 App 的核准相同：核准時建立一趟出車中的車趟（預計的時間、申請的車牌、同車最後一趟的結束里程、申請人的姓名、可指派駕駛人），
申請改為「已核准」並記下產生的車趟；兩筆在同一個交易寫入。退回要填原因。只有「待簽核」的申請可以處理。
重送同一個核准不會產生第二趟車趟：第二次時申請已不是待簽核（`409 request_not_pending`）。

## 6. 查詢的規則

- 搜尋以空白分成字詞，每個字詞都要出現在該種類的搜尋欄位；英文字母不分大小寫（只轉換 ASCII，三種實作一致）。
- 排序：數字在文字前，**沒有值的一律在最後**；相同時依 UUID。文字以碼位比較（不是依語言的排序規則，三種實作一致）。
- 資料量：清單在主機上讀取同一種類的有效資料後篩選與分頁。車隊規模（數千到數萬筆車趟）沒有問題；Cloudflare 免費方案的 CPU 時間很短，
  資料很多時建議付費方案或 Docker／PHP 版（全量同步 `GET /snapshot` 也有相同的考量）。

## 7. 個資

- 修改前後歷史保存完整內容（還原與比較需要），但網頁與 API 預設遮蔽駕駛人的電話、證號（只顯示最後 3 個字）與備註；
  管理員按「顯示個資」（`pii=1`）才看到完整內容，並在稽核紀錄留下「檢視個資」。
- 稽核紀錄不寫入駕駛人的個資（只有 UUID 與姓名）；升級到 1.2.0 時清除 1.0–1.1 留下的駕駛人摘要。詳見 [`audit-history.md`](audit-history.md)。

## 8. 網頁管理的畫面（1.2.0）

側欄 13 個區塊（手機寬度時在上方，可橫向捲動）：

| 區塊 | 內容 |
| --- | --- |
| 總覽 | 裝置、車輛、駕駛人、出車中、待簽核、配對碼、即時位置的數量；待簽核的申請、出車中的車趟、最近的修改、主機資訊 |
| 使用者與駕駛 | 駕駛人清單 → 詳情（車趟、巡檢、用車申請、綁定的裝置）、修改基本資料（電話、證號、駕照到期、備註） |
| 裝置 | 配對的 App 與瀏覽器：角色、綁定駕駛人、網頁的登入方式（記住／不記住、舊的登入方式）與登入期限、最近連線（App 每小時、網頁每 5 分鐘更新）、建立的車趟、解除配對 |
| 車輛 | 清單（到期提示）→ 詳情（車趟、保養、工單、巡檢、用車申請）、修改、刪除（影響預覽） |
| 車趟 | 清單（狀態、車輛、駕駛人、期間、搜尋、排序）→ 詳情（出回車、里程、費用、出發定位與即時位置、巡檢、工單、申請）、修改、回車 |
| 用車申請 | 清單（待簽核數量顯示在側欄）→ 詳情 → 核准（可指派駕駛人）或退回 |
| 巡檢與工單 | 兩個子分頁；工單可改狀態（完工在 App）、負責人、備註 |
| 保養與零件 | 保養紀錄、保養項目、零件三個子分頁；零件顯示低於安全庫存 |
| 即時位置 | 出車中車輛最近一次回報的位置（每 20 秒更新） |
| 報表 | 期間、車輛、駕駛人篩選；費用、里程、稼動率、依車輛／駕駛人／成本中心／日期；CSV 下載（[`reports.md`](reports.md)） |
| 修改歷史與稽核 | 修改前後歷史（依資料、套用結果、來源篩選；每筆可看差異）、稽核紀錄 |
| 配對碼 | 建立（管理員配對碼要再確認）、撤銷 |
| 主機設定 | 主機名稱、派車預設值、主機資訊、這個瀏覽器、網頁管理的網址 |

共同的做法：

- 網址記住畫面與篩選條件（例如 `#trips?status=active&plate=ABC-1234`、`#r/trip/<UUID>`），重新整理或分享網址會回到同一個畫面。
- 清單：搜尋、篩選、點欄位標題排序、分頁；手機寬度時篩選收在「篩選」裡、表格可以橫向捲動、次要欄位隱藏。
- 修改：表單依資料規格產生（型別、範圍、必填）→「預覽變更」由主機檢查並列出差異與提醒 → 填原因（有常用原因可選）→「確認儲存」。
  主機回報的欄位錯誤顯示在欄位下；期間被其他裝置改過時提示重新載入。
- 刪除：先列出會一併刪除的資料與不能刪除的原因，輸入確認文字（車輛是車牌）與原因才能刪除。
- 詳情頁的修改前後歷史可以比較任兩個版本；駕駛人的個資預設遮蔽，「顯示個資」會先確認並記在稽核紀錄。
- 讀取中顯示「載入中…」；錯誤顯示原因與「重試」；伺服器資料一律以文字顯示（不當成 HTML）。

## 9. 語言

網頁管理在 1.2.0 只有繁體中文（台灣）。評估過日文：介面約 500 個字串直接寫在 `web/admin.js`，要支援日文需要先把字串抽成對照表、
完整翻譯並由懂日文的人審閱（含日期、數字與錯誤訊息）；只加語言選單而沒有完整翻譯不符合要求，所以 1.2.0 不提供語言切換，列為之後的版本的工作。
主機的 API 錯誤訊息也是繁體中文；App 依自己的語言顯示。

## 10. 測試

[`conformance/admin-suite.mjs`](../conformance/admin-suite.mjs)（由 `api.test.mjs` 呼叫）在三種實作執行：清單的搜尋、篩選、排序（沒有值在最後）、分頁；
詳情的關聯；修改的預覽、原因、版本衝突、欄位與各種類規則、關聯檢查；舊的離線修改被略過並留下摘要；回車與即時位置；
刪除的影響預覽、出車中的車趟、筆數改變、不可分割的連鎖刪除；核准與退回；歷史的個資遮蔽與「檢視個資」稽核；權限。

網頁管理的畫面另有選用的瀏覽器實測 [`scripts/check-admin-ui.mjs`](../scripts/check-admin-ui.mjs)（需要另外安裝 Playwright，不在 `package.json` 中）：
登入、13 個區塊、清單的篩選與排序、詳情與關聯、修改（預覽 → 原因 → 儲存）、欄位錯誤、回車、核准、刪除的影響預覽、個資遮蔽、報表與 CSV 下載、
手機寬度沒有橫向捲動、主控台沒有錯誤。
